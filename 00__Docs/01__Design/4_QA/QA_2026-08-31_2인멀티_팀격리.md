## 실행 방식 — 실제로 2인으로 붙였다

정적 검수가 아니다. **NGO Host 1 + Client 1을 실제로 접속시켜 밤 → 전환 → 낮 → 다음 밤을
한 바퀴 돌렸다.**

| 항목 | 값 |
|---|---|
| Host | 메인 체크아웃 에디터 (pid 45220), `clientId=0`, **팀 0** |
| Client | MPPM 가상 플레이어 `Player 2` (`Library/VP/mppma93061e5`), `clientId=1`, **팀 1** |
| 트랜스포트 | `UnityTransport` 127.0.0.1:7777 |
| 접속 경로 | 양쪽 다 `Battle_01`을 연 채 재생 → `NetworkAutoStart`가 메인은 `StartHost`, 클론은 `StartClient` |
| 좌석 | `MatchSeating.SeatServer`의 `NoPreference` 경로. 빈 팀 우선 배정으로 0 / 1로 갈렸다 |
| 진행 | 1일차 밤 → 전환(귀환 정산) → 1일차 낮(판매·임대료) → 2일차 밤 |

**서로 다른 팀 2개로 확인했다** — 한 팀에 몰아넣지 않았다.

### 접속 전에 반드시 확인할 것 — `NetworkConfig` 해시

이번 재검증에서 **세 판을 헛돌린 뒤에야** 원인을 찾았다. 클라이언트가 붙자마자 서버에
끊겼고 호스트 콘솔에는 한 줄만 남았다:

```
[Netcode] NetworkConfig mismatch. The configuration between the server and client does not match
   ConnectionRequestMessage.Deserialize (line 146)
```

`NetworkConfig.GetConfig()`(NGO `Runtime/Configuration/NetworkConfig.cs:328`)는 `ForceSamePrefabs`가
켜져 있으면 **네트워크 프리팹의 `GlobalObjectIdHash`를 전부 해시에 넣는다.** 낡은 MPPM 클론은
자기 Library의 낡은 GUID 매핑으로 다른 값을 계산했다.

| 프리팹 | 낡은 클론 | 정상 |
|---|---|---|
| Player | 354678369 | 일치해야 함 |
| Customer | 2373786948 | 일치해야 함 |
| DroppedPile | 3890980858 | 일치해야 함 |

클론을 껐다 켜는 것으로는 고쳐지지 않았다. **클론 디렉터리를 Library까지 통째로 지우고**
MPPM이 새 id로 다시 만들게 해야 풀렸다. 재생성 뒤 양쪽 `configHash`가
`10887699380221002848`로 일치했고 그때부터 접속이 됐다.

**앞으로 2인 검증은 접속 확인 전에 양쪽 `configHash`부터 대조한다.** 이 확인 없이 배터리를
돌리면 "격리가 잘 된다"가 아니라 "애초에 붙지 않았다"를 통과로 착각한다.

### 교차 팀 공격을 재현한 방법

클라이언트는 **상대 팀 카페를 애초에 볼 수 없다**(T-3). 이번 세션에서도 클라이언트가 본
`IngredientShelf` 중 남의 팀 것은 **0개**였다. 정상 클라이언트로는 그 RPC를 보낼 대상 자체가
없다. 그래서 서버 프로세스에서 **NGO가 수신 시 실행하는 것과 같은 경로**를 그대로 태웠다:

- `NetworkBehaviour.__rpc_exec_stage`를 `Server`로 세우고
- `RpcParams.Receive.SenderClientId = 1`(클라이언트의 실제 id)로 채워
- `UseRpc` / `TakeRpc` / `ServeRpc` 본문을 호출

이 탐침이 실제 수신 경로와 같다는 것은 **전선을 타는 진짜 RPC로 대조**해 확인했다(T-10).
모든 케이스에 양성 대조를 붙여, "아무 일도 안 일어난 것"이 가드 때문인지 탐침이 죽은
것인지 구분했다.

```

client : scene=Title
         isClient=False connected=False listening=False
         shutdownReason='Disconnected due to host shutting down.'
         players=0  cafes=0  director=False
```

`SteamLobby.OnNetworkStopped`(`Assets/Scripts/Net/SteamLobby.cs:634-652`)가 `OnClientStopped`로

(`players=0 cafes=0`), 씬을 넘어 사는 `SteamLobby`는 살아남았다 — 설계대로다.
**종료 전후로 클라이언트·호스트 양쪽에 새 예외가 하나도 생기지 않았다.**

### T-10. 클라이언트가 전선을 타고 보낸 RPC가 실제로 통한다 ✅

T-2의 탐침이 실제 수신 경로와 같다는 것을 증명하기 위한 대조다. 서버가 클라이언트를
자기 팀 선반 앞에 세운 뒤, **클라이언트 프로세스에서** `shelf1.TakeRpc((int)Ingredient.Bean)`를
호출해 진짜 네트워크 메시지를 보냈다.

```
client : localId=1 team=1 visibleSpawned=23
         shelves visible: own=True  otherTeam=0
         sent TakeRpc(Bean) on own shelf over the wire
host   : server sees client1 carry: empty=False held=Bean
```

같은 서버 진입점이 실제 전송으로도 동작하고, 클라이언트에게 **남의 팀 선반은 0개**로
보인다는 것까지 같이 확인됐다.

### N-1. 2인만 붙은 상태에서 UnityTransport 수신 큐가 포화됐다

- **실제 결과:** 클라이언트 콘솔 (2026-08-31T15:32:04Z, 낮 배터리 실행 중)

  ```
  Receive queue is full, some packets could be dropped, consider increase its size (128).
    Unity.Networking.Transport.TopLa... (Burst job)
  ```

- **기대 결과:** 2인 세션에서 수신 큐가 포화되지 않는다.
- **영향 범위:** 기획서 10장은 최대 **4팀 8인**을 지원한다. 2인에서 이미 기본 큐가 찬다면
  8인에서는 더 이르고 빈번하게 찬다. NGO의 신뢰성 채널은 재전송하지만, 비신뢰·단편화
  메시지는 실제로 유실될 수 있다.
- **의심 지점(미확정):** 접속 직후 몰리는 버스트가 후보다 — `FogSnapshotRpc`가 걷힌 칸
  296개를 한 번에 싣고(`FogOfWar.cs:209`), 카페 스폰과 박스 17개 상태 전송이 같은 구간에
  겹친다. **어느 메시지가 큐를 채웠는지는 확인하지 못했다.** Network Profiler로
  메시지별 크기·빈도를 재야 확정된다.
- **재현 절차:** 위 「실행 방식」대로 2인 접속 → 낮 페이즈까지 진행 → 클라이언트 콘솔 확인.

### D-3. 조치 — 체크리스트를 고치는 대신 없앴다

D-1·D-2를 "올바른 규칙으로 바꾼다"로 처리하려 했으나 그것이 문제의 반복이었다.
`AGENTS.md`는 에이전트 작업 계약이지 기획 규칙의 저장소가 아니다. 규칙을 여기에 옮겨 적으면
기획서와 두 벌이 되고, 기획이 바뀌는 날 조용히 갈라진다 — 이번에 틀린 두 줄이 생긴 경위가
정확히 그것이다.

그래서 **확인 항목 목록 5줄을 통째로 지우고**, 판정 기준을 기획서로 넘겼다.

```diff
-- **2인 멀티플레이를 반드시 실제로 검증한다.** NGO Host 1 + Client 1(MPPM 가상 플레이어 포함)
-  이상으로 붙여 한 판을 돌린다. ... 2인에서 확인할 항목은 최소 다음과 같다.
-  - 팀 배정이 두 클라이언트에 각각 붙고, 클라이언트마다 자기 팀 값을 읽는가
-  - 남의 카페 설비·재료 칸·서빙대·싱크대·완성 게이지를 조작할 수 없는가
-  - 안개·박스 개봉·팀 재고·매출·임대료가 팀별로 분리되는가
-  - 한쪽의 행동이 다른 쪽의 상태를 바꾸지 않는가
-  - Host가 종료했을 때 Client가 안전하게 빠져나오는가
+- **2인 멀티플레이를 기준 기획서를 기반으로 반드시 실제로 검증한다.** NGO Host 1 + Client 1
+  (MPPM 가상 플레이어 포함) 이상으로 붙여 한 판을 돌린다. 팀 격리는 서로 다른 팀 2개로
+  확인한다 — 한 팀만 띄우면 팀 간 오염 결함은 드러나지 않는다. 무엇을 확인해야 하는지는
+  여기 적지 않는다. 기획서에서 읽는다.
```

이 보고서의 T-1 ~ T-10은 지워진 목록이 아니라 **기획서 3.1 / 3.2 / 3.3 / 5장 / 6.1 / 6.6을
근거로** 판정한 것이다. 근거 장·절은 각 항목에 그대로 남아 있다.

### U-1. 클라이언트 화면 표시

### U-2. 3인 이상 / 한 팀 2인 구성

### U-3. N-1의 원인 메시지 특정

수신 큐를 채운 것이 어느 RPC인지 확정하지 못했다. Network Profiler 필요.

## 관찰 — 결함으로 단정하지 않는다

**프리팹에 직렬화된 `GlobalObjectIdHash`와 에디터가 계산하는 값이 다르다.**

| 프리팹 | 에셋 파일에 적힌 값 | 에디터가 계산한 값 |
|---|---|---|
| `Assets/Prefabs/Player.prefab:124` | 4269354122 | 354678369 |
| `Assets/Prefabs/Customer.prefab:133` | 1637413538 | 2373786948 |
| `Assets/Prefabs/DroppedPile.prefab:130` | 4097624786 | 3890980858 |
| `Assets/Prefabs/Cafe.prefab:243` | 3123497839 | 3123497839 (일치) |

에디터끼리는 양쪽 다 다시 계산하므로 문제가 드러나지 않는다(이번 세션이 그렇다).
다만 `GlobalObjectIdHash`는 `OnValidate`가 에디터에서만 채우는 값이라, **빌드는 파일에 적힌
쪽을 싣는다.** 빌드 클라이언트와 에디터 호스트를 붙이면 이번에 겪은 것과 같은
`NetworkConfig mismatch`가 날 수 있다.

**빌드 ↔ 에디터 조합은 실제로 시험하지 않았다.** 위 표는 확인된 사실이고, 빌드에서
실패한다는 것은 추론이다. 다음 QA에서 빌드 클라이언트로 확인할 값이다.

**클라이언트 콘솔의 `NullReferenceException`은 게임 코드가 아니다.**
스택이 `UnityEditor.EditorWindow.Close()` → `EditorApplication.Internal_CallDelayFunctions`뿐이고,
같은 시각 `Attempted to open unsupported window in cloned player systems: FallbackEditorWindow`
경고가 5건 함께 찍혔다. MPPM 클론의 에디터 창 처리이며, 클론 기동 시각(15:30:14)에 발생해
검증 구간과 겹치지 않는다.
