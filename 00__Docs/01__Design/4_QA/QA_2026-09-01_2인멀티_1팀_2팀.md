## 반드시 먼저 — 접속 전에 `NetworkConfig` 해시를 대조한다

클라이언트가 붙자마자 서버에 끊기고 호스트 콘솔에 한 줄만 남는 경우가 있다.

```
[Netcode] NetworkConfig mismatch. The configuration between the server and client does not match
   ConnectionRequestMessage.Deserialize (line 146)
```

`NetworkConfig.GetConfig()`는 `ForceSamePrefabs`가 켜져 있으면 네트워크 프리팹의
`GlobalObjectIdHash`를 전부 해시에 넣는다. 낡은 MPPM 클론은 자기 Library의 낡은 GUID
매핑으로 다른 값을 낸다. **클론 재시작으로는 안 고쳐지고, `Library/VP/mppm*`를 통째로
지워 MPPM이 새 id로 다시 만들게 해야** 풀린다.

이 확인 없이 배터리를 돌리면 "격리가 잘 된다"가 아니라 "애초에 붙지 않았다"를 통과로
착각한다. 이번에도 이것 때문에 세 판을 헛돌렸다.

## 높음

### H-1. 서버가 플레이어를 순간이동시키면 클라이언트는 자기를 엉뚱한 좌표에서 본다

- **심각도:** 높음
- **파일:** `Assets/Scripts/Player/PlayerPrediction.cs:81`
- **기획서 근거:** 6.8 "밤 페이즈 진입: 정해진 소환 위치에서 시작", 5장 귀환 정산.
  두 규칙 모두 `PlayerTeam.MoveToPhaseStartServer`(`Assets/Scripts/Player/PlayerTeam.cs:94-104`)
  → `PlayerTeleport.ToServer`를 탄다. **매 페이즈 전환마다 모든 플레이어에게 걸리는 경로다.**

**재현 절차** (구성 B, 낮 페이즈)

1. 서버와 클라이언트가 같은 좌표를 볼 때까지 둔다.
2. 서버에서 `PlayerTeleport.ToServer(client1Player, new Vector3(70, y, 0))` 한 번.
3. 클라이언트 프로세스에서 자기 `PlayerObject.transform.position`을 읽는다.

**실제 결과**

```
-- settled
SERVER sees client1 at (136.00, 1.08, -20.00)
CLIENT sees itself at (136.00, 1.08, -20.00)      ← 일치

-- single teleport to (70, 0)
server teleported client1 to (70.0, 1.1, 0.0)

-- after
CLIENT sees itself at (4.00, 1.08, 20.00)          ← 서버는 (70, 0)
```

**기대 결과:** 클라이언트도 `(70, 0)`.

`(4, 20) = (70, 0) + [(70, 0) − (136, −20)]` — **텔레포트 델타가 정확히 한 번 더 적용됐다.**

**원인**

```csharp
// PlayerPrediction.cs:78-83
if (diff.magnitude > snapDistance)
{
    SnapTo(transform.position + diff);   // = 현재 + (서버 − 예측)
    return;
}
```

스냅은 **절대 위치**로 가야 하는데 **상대 델타**를 더한다. `현재 == 예측`일 때만 우연히
`서버`와 같아지고, 어긋나면 그 어긋남이 남는다. 델타가 두 번 적용되는 경로가 있어
오차가 텔레포트마다 누적된다 — 연속 텔레포트에서는 배로 커졌다.

```
(70,0)→(70,0) 텔레포트 : 클라이언트 (158.59,-12.59) → (114.59,-52.59)
(70,0)→(0,0)  텔레포트 : 클라이언트 (114.59,-52.59) → (-114.59, 52.59)
                          역산한 예측값 (229.18,-105.18) = 현재의 정확히 2배
```

**영향 범위**

- `Predicting => IsSpawned && IsOwner && !IsServer`이므로 **클라이언트에서만** 난다.
  호스트 혼자 테스트하면 절대 드러나지 않는다.
- 서버의 모든 거리 판정(`Station.InReach`, `Counter.OnServingSide`, `ItemBox.InReach`,
  `ReturnZone` 구역 판정)은 **서버 좌표**를 쓴다. 클라이언트는 자기가 보는 자리에서
  아무것도 조작할 수 없고, 남들에게는 다른 자리에 서 있는 것으로 보인다.
- 귀환 판정도 서버 좌표로 하므로, 화면상 귀환 지점에 서 있어도 소실 판정이 날 수 있다.

**확인하지 못한 것:** 델타가 정확히 몇 번, 어느 경로로 두 번 적용되는지는 특정하지 못했다.
`ReconcileClient`가 이력 미스로 버리는 가설은 **배제됐다** — 클라이언트에서 이력을
직접 읽어 확인했다.

```
history capacity=60   recorded ticks 28740..28799
is the CURRENT serverTick(28756) in history? True
pending error=(0.000, 0.000, 0.000)
```

**간헐적이다.** 밤→전환 직후 한 번은 클라이언트가 `(136,-20)`으로 정확히 따라왔다.
정합 상태에서도 실패하는 위 재현이 있으므로 결함은 확정이나, 매번 나지는 않는다.

**수정 방향(제안):** 스냅 분기는 권위 좌표를 그대로 쓴다 — `SnapTo(serverPosition)`.
상대 보정은 데드존~스냅 사이의 부드러운 교정에만 남긴다.

> "10초 동안 입력 없음 → 타버린다"와 일치한다.

## 관찰 — 결함으로 단정하지 않는다

**프리팹에 직렬화된 `GlobalObjectIdHash`와 에디터가 계산하는 값이 다르다.**

| 프리팹 | 파일에 적힌 값 | 에디터 계산값 |
|---|---|---|
| `Assets/Prefabs/Player.prefab:124` | 4269354122 | 354678369 |
| `Assets/Prefabs/Customer.prefab:133` | 1637413538 | 2373786948 |
| `Assets/Prefabs/DroppedPile.prefab:130` | 4097624786 | 3890980858 |
| `Assets/Prefabs/Cafe.prefab:243` | 3123497839 | 3123497839 (일치) |

에디터끼리는 양쪽 다 재계산하므로 드러나지 않는다. 다만 `GlobalObjectIdHash`는
`OnValidate`가 에디터에서만 채우므로 **빌드는 파일에 적힌 쪽을 싣는다.** 빌드 클라이언트와
에디터 호스트를 붙이면 위 `NetworkConfig mismatch`가 날 수 있다.
**빌드 조합은 시험하지 않았다** — 표는 사실이고, 빌드에서 실패한다는 것은 추론이다.
