# 루이지 UI 시안 → 실제 인게임 적용 계획

작성일: 2026-10-17

## 목표와 완료 기준

`blood-beans-luigi-portable.html`의 루이지 콘셉트를 실제 게임에서 작동하는 UI로 재현한다. 시안으로 외형·배치를 정하고, 기존 프로젝트의 데이터와 입력 연결을 활용한다. 주요 패널의 실루엣, 초록·크림·황동 재질, 입체 글자, 아이콘, 크기와 간격을 실제 플레이 캡처로 대조한다.

완료 결과는 적용된 Unity 프리팹·스프라이트·폰트/머티리얼, 실제 게임 데이터 연결, 화면별 시안 대조 캡처다. 인게임 화면 교체와 기능 연결은 아직 시작하지 않았다. 2026-10-18에 별도 PrototypeKit 폴더에 실제 검토용 에셋과 공통 프리팹을 추가했다. 검토 범위와 결과는 UI_PRODUCTION_REVIEW.md에 기록했다. 기존 게임 화면·씬은 교체하지 않았다.

## 기준

- 시각 기준 파일은 이 폴더의 `blood-beans-luigi-portable.html`이다. 기본 적용 대상은 갤러리의 `현재 시안`이며 절제형은 비교 자료로 둔다. 캐릭터 선택은 여러 명을 함께 보여주는 요구를 반영한다.
- 화면별 적용 기준 이미지를 하나씩 기록한다. 폰트 모드와 선택값도 함께 기록해 서로 다른 버전을 섞지 않는다.
- 현재 추가된 실제 폰트들은 최종 확정 서체로 간주하지 않는다. 글자 재현은 대표 화면 제작에서 우선 해결한다.
- 시안의 비교판은 상태들을 설명하기 위해 한꺼번에 펼친 자료다. 주문·제조·가방의 여러 상태를 실제 게임에서는 상황에 맞는 개별 부품으로 표시한다.
- 낮에는 가방을 표시하지 않는다. 밤에는 시야를 가리지 않는 작은 가방과 적재량을 사용한다.
- 비교 캡처는 같은 해상도·게임 카메라·상태에서 만든다. HUD 작업 중 카메라를 움직여 외형 차이를 가리지 않는다.
- 이번 제작 범위는 UI와 그 외형을 구현하는 데 필요한 UI용 3D 부품이다. 클립보드 판·금속 클립·두꺼운 프레임·버튼 등은 포함한다. 게임 월드의 프랍·배경·캐릭터 모델을 새로 제작하거나 재디자인하는 작업은 제외한다. 캐릭터 선택 화면은 기존 모델을 UI에 표시·배치하는 범위로 다룬다.

## 확인한 현재 구조

- UI 프리팹: `BloodAndBeans/Assets/Art/UI/Prefabs/Screen`, `Popup`, `Parts`.
- UI 코드: `BloodAndBeans/Assets/Scripts/Client/UI`.
- `UIManager`는 화면/팝업 스택과 Addressables 로딩·해제를 관리한다.
- `UIThemeConfig`는 공통 팔레트·규격·글자 배율을 관리한다. `UIFontScale`은 기본 크기에 배율을 적용하며 최종 크기로 만든 영역을 제외하는 기능이 있다.
- `UIMatchHudScreen`은 HUD와 화면 좌표 표식 층, 제조 카드의 표시 위치를 관리한다.
- `UICustomerOrder`는 주문 아이콘·가격·인내심·경고 상태를 표시한다. 사용한 인내심을 말풍선 안에서 아래부터 채우는 기존 규칙이 있다.
- `UIMakingCard`는 현재 재료와 제품 상태를 받아 이름·아이콘·재료 목록·완성/실패 상태를 표시한다.
- 기존 타이틀, HUD, 스킬, 메뉴·재료 아이콘도 있으므로 시안과 대조해 재사용 여부를 판단한다.
- 시안 자료에는 전체 장면 이미지, 글자 없는 템플릿, 알파가 있는 메뉴/주문/루팅/밤 부품 비교판이 있다. 이것들이 곧바로 개별 게임용 스프라이트 세트인 것은 아니다.

현재 에디터의 실제 배선·재생 결과는 이번 계획에서 조회하거나 검증하지 않았다. 구현 시작 시 Unity CLI로 프로젝트와 에디터 상태를 확인한다.

## 1. 화면별 제작 명세 작성

전체 18개 항목을 기존 화면·팝업·부품에 대응시킨다. 각 요소에 다음을 기록한다.

- 시안 기준 좌표·최종 표시 크기·앵커·레이어 순서.
- 고정 장식 / 고정 문구 / 가변 문구 / 아이콘 / 게이지 / 3D 표현의 구분.
- 필요한 상태: 기본, 호버, 눌림, 선택, 비활성, 성공, 경고, 실패 등 해당 요소에 실제 필요한 것만.
- 기존 데이터·이벤트·프리팹 연결점과 새로 제작할 그래픽.

1920×1080을 일차 대조 기준으로 삼는다. CanvasScaler와 `UIFontScale`을 함께 확인해 최종 크기가 중복 확대되지 않도록 한다.

**산출물:** 화면-부품 대응표, 에셋 제작 목록, 시안과 현재 표시 규칙 사이의 차이 목록.

## 2. 시안을 구현용 그래픽으로 분리

| 요소 | 구현용 제작 방식 |
| --- | --- |
| 초록 패널·버튼 | 문자와 아이콘을 분리한 투명 스프라이트. 늘어나는 영역은 9-slice로 만들고 고유한 모서리·황동 장식은 형태를 유지한다. |
| 클립보드·간판·곡선 프레임 | 판의 두께·모서리·곡면·금속 클립을 UI용 공통 3D 원형으로 제작할 수 있다. 고정 표현은 투명 렌더 스프라이트, 시점/반사/부품 움직임이 필요한 표현은 실시간 3D로 표시한다. 실루엣과 명암을 유지한다. |
| 가격 탭·선택선·체크·키 힌트 | 독립 부품과 상태별 표현으로 분리한다. |
| 주문 인내심·쿨타임·판정 게이지 | 프레임과 채움/침/상태 표시를 분리해 실제 값으로 움직이게 한다. |
| 가방·스킬·보석 | 최종 표시 크기에서 같은 재질·명암·선 굵기를 갖는 투명 아이콘을 준비한다. |
| 음료·재료 아이콘 | 기존 게임 모델을 이용한 동일 조명·카메라의 썸네일 또는 기존 UI 아이콘을 활용한다. 이번 범위에서는 제품·재료 모델 자체를 새로 제작하지 않는다. |
| 글자 | 제목·본문·숫자별 실제 렌더링 방식과 머티리얼을 준비한다. |

모든 부품은 게임에서 보이는 크기로 검수한다. 가장자리, 투명 배경, 눌림·선택 상태까지 확인한 뒤 프리팹에 넣는다.

## 3. 글자 재현과 대표 화면 제작

먼저 낮 HUD·주문 말풍선·제조 카드가 함께 보이는 실제 플레이 화면을 완성한다. 이 화면에서 패널, 3D 아이콘, 작은 글자, 수치, 상태 변화까지 한 번에 검증한다.

서체는 다음 두 종류로 작업한다.

- 가변 문구·이름·매출·시간: 실제 TMP 폰트 에셋과 공용 머티리얼로 구현한다. 외곽선, 입체 음영, 폭, 자간, 숫자 폭과 기준선을 시안에 맞춘다. 임의의 기존 후보를 최종 서체로 확정하지 않는다.
- 고정 로고·특수한 제목 레터링: 실제 서체만으로 형태가 맞지 않으면 시안 형태를 살린 독립 레터링 스프라이트를 사용한다. 변경되는 본문과 수치는 분리한다.

생성 이미지 속 글자가 실제 폰트와 일치한다고 가정하지 않는다. 시안과 실제 Unity 글자 샘플의 차이를 먼저 줄인다. 한글·숫자·기호 누락과 작은 크기에서의 뭉침도 함께 확인한다.

**첫 중간 결과:** 실제 게임 캡처, 같은 해상도의 시안 대조 이미지, 구현용 개별 부품, 실제 값으로 변하는 주문·제조·HUD.

## 4. 프리팹 구성과 기존 기능 연결

기존 `Screen / Popup / Parts`와 컴포넌트 책임을 활용한다. 반복 부품은 자기 내부 참조와 상태 표현을 소유하고 화면은 그 부품에 데이터와 이벤트를 전달한다. 필요한 새 부품만 기존 폴더 안에 추가한다.

| 적용 대상 | 주요 기존 연결점 | 작업 |
| --- | --- | --- |
| 낮/밤 HUD | `UIMatchHudScreen`, `MatchHudPresenter` | 시계·매출·팀 순위·스킬·가방·안내를 시안 배치와 부품으로 적용. |
| 주문·제조·판정 | `UICustomerOrder`, `UIBubbleFill`, `UIMakingCard`, `UICompletionGauge`, `UICraftingJudgement` | 실제 주문·재료·인내심·판정과 새 그래픽을 연결. |
| 조합법·루팅 | `UIRecipeRow`, `UIBoxLootPopup`, `UIBoxLootSlot` | 반복 행·슬롯과 선택·비활성·공개 상태 적용. |
| 캐릭터·팀 선택 | `UICharacterSelectScreen`, `CharacterStage`, 팀/캐릭터 부품 | 실제 모델을 여러 명 함께 배치하고 이름·팀·선택·준비 상태 연결. |
| 입장 화면 | `UITitleMenuScreen`, `UIRoomListScreen`, `UIRoomScreen` | 타이틀·버튼·목록·상세 패널과 기존 입장 흐름 연결. |
| 결과·공통 | 정산/결과/귀환/설정/로딩/전환 컴포넌트 | 공통 재질·글자·버튼을 재사용하고 기존 표시 조건 연결. |

화면 등록·Addressables 참조·팝업 입력 소유·뒤로 가기·재접속 시 수명을 함께 확인한다. 게임 규칙과 서버 상태의 권위는 기존 계층에 두고 UI는 그 값을 표시한다. 기능상 필요한 표현 코드만 수정한다.

### 4.1 공통 프리팹을 여러 곳에 쓰는 기준

기본 구조는 **공통 외형 부품 + 내용 영역 + 용도별 동작 컴포넌트**로 구성한다. 기존 `UIThemeConfig`와 부품의 직렬화 설정을 우선 활용한다.

| 공통 원형 | 사용처 예시 | 조정할 설정 |
| --- | --- | --- |
| 클립보드 프레임 | 조합법·주문 상태 비교·제조·정산의 해당 패널 | 표시 크기, 클립 위치, 안쪽 여백, 외형 스킨, 내용 영역 |
| 버튼 | 타이틀·입장·준비·설정 | 문구, 아이콘, 크기, 강조/보조 스타일, 입력 이벤트 |
| 아이콘 슬롯 | 재료·제품·루팅·스킬 중 구조가 같은 것 | 아이콘, 수량, 사용 가능 여부, 선택/경고 표시 |
| 키 힌트·값 라벨 | HUD·상호작용·귀환 안내 | 키, 문구/수치, 아이콘, 상태색 |

값만 다른 경우 같은 프리팹 인스턴스의 설정을 바꾼다. 안정적인 구조 차이가 있을 때 Prefab Variant를 사용하고, 동작·수명·입력 역할이 다른 부품은 공통 프레임/슬롯만 공유한다. 모든 기능을 하나의 거대한 만능 프리팹에 옵션으로 넣지 않는다.

클립보드 크기를 바꿀 때 2D는 9-slice로 모서리와 테두리를 보존한다. 실시간 3D는 판의 너비·높이를 조정하되 클립·테두리 두께가 늘어나지 않도록 분리한다. 필요한 규격의 메시를 에디터에서 제작해 재사용하고, 매 프레임 메시를 다시 만들지 않는다.

### 4.2 UI용 3D 부품의 구현 가능성과 선택

**클립보드 같은 UI용 하드서피스 부품은 구현 가능하다.** 현재 시안은 렌더 결과 이미지이며 메시·UV·머티리얼이 포함된 원본 모델은 없으므로, 구현용 모델 제작은 별도 작업으로 포함한다. 단순 판·테두리·클립은 Unity에서 메시를 제작·조립하는 방식으로 시작할 수 있다. 복잡한 고유 장식은 형상을 확인한 뒤 별도 모델링 필요 여부를 정한다.

대표 구조는 다음과 같다. 이는 새 부품의 설계 예시이며 현재 존재하는 프리팹 이름을 뜻하지 않는다.

```text
클립보드 부품
  외형: 둥근 판 / 테두리 / 금속 클립 / 접촉 음영
  내용: 제목 / 가변 본문·수치 / 아이콘·슬롯
  상태: 선택·강조·비활성·등장 연출
```

- **고정 방향의 클립보드:** 3D 원형에 재질·조명을 맞추고 투명 배경으로 렌더한 스프라이트를 사용한다. 판의 두께·금속 곡면·그림자를 이미지에 보존하며, 글자와 슬롯은 별도 uGUI 부품으로 갱신한다. 대다수 고정 HUD/패널의 우선 검토안이다.
- **실제 기울기·깊이·움직이는 반사가 필요한 클립보드:** 모델과 그 면에 정렬된 내용을 함께 표시한다. 필요하면 UI 전용 렌더 스테이지/카메라와 RenderTexture로 합성한다. 내용이 판 위에서 미끄러지거나 클립의 앞뒤 순서가 어긋나지 않도록 투영과 가림 순서, 입력 좌표를 같이 확인한다.
- **클립/버튼 일부만 움직이는 경우:** 전체 패널을 매 프레임 3D 렌더링할 필요가 있는지 먼저 비교한다. 별도 레이어·상태 스프라이트·UI 애니메이션으로 같은 결과를 낼 수 있으면 그 방식을 사용한다.

3D 모델 제작 여부와 실행 중 실시간 3D 렌더링 여부를 따로 결정한다. 원형은 공유하면서 사용처에 따라 스프라이트 또는 실시간 표시를 고를 수 있다. 시안의 입체감과 곡면을 유지한 상태에서 비용을 비교한다.

**첫 검증 부품:** 같은 클립보드 원형으로 조합법 크기와 제조 카드 크기를 구성한다. 두 규격에서 클립 비율·판 두께·문구 정렬이 유지되는지, 기존 UI 데이터가 정상 갱신되는지 확인한다. 실시간 연출이 필요한 경우에는 고정 렌더 버전과 실시간 3D 버전을 같은 표시 크기로 비교한다.

### 4.3 처음부터 고려할 최적화

같은 프리팹을 여러 곳에서 쓰는 것 자체가 드로콜이나 인스턴스 수를 줄여 주지는 않는다. 공통화는 중복 에셋과 유지보수 비용을 줄이고, 실행 비용은 다음 항목을 별도로 확인한다.

- **공유 자원:** 메시·스프라이트·폰트 아틀라스·머티리얼을 공유한다. UI 개별 색상/밝기는 가능한 범위에서 Graphic 정점 색으로 전달하고, 카드마다 머티리얼을 복제하지 않는다.
- **텍스처:** 최종 표시 크기에 맞춰 제작한다. 함께 표시·로드되는 UI끼리 아틀라스를 구성하고, 모든 화면을 하나의 큰 아틀라스에 넣어 불필요하게 상주시킬지 여부는 로딩 범위와 같이 판단한다.
- **Canvas/TMP 갱신:** 정적 장식과 자주 바뀌는 수치의 갱신 범위를 고려한다. 값이 바뀔 때만 문구·슬롯을 갱신하고, 부품마다 Canvas를 무조건 추가하지 않는다. TMP 머티리얼 프리셋과 필요한 글리프/폴백을 공유한다.
- **수명과 재사용:** 기존 화면 캐시·Addressables 로드/해제 흐름을 활용한다. 반복 생성·삭제 비용이 측정되는 말풍선/피드백 등은 기존 풀과 수명 규칙을 확인한 뒤 필요한 범위만 재사용한다.
- **UI용 실시간 3D:** 부품마다 전용 카메라·조명을 만들지 않는다. 동시에 보이는 수와 수명에 맞춰 스테이지/렌더 자원을 공유한다. 닫힌 UI의 렌더링을 중단하고 고정 상태에서 매 프레임 갱신이 필요한지 검토한다. RenderTexture 해상도는 실제 표시 크기를 기준으로 정한다.
- **그림자와 효과:** 고정 UI의 접촉 음영·반사는 베이크된 결과를 우선 비교한다. 실시간 그림자·블러·발광·마스크·큰 투명 영역의 비용은 시안 재현에 필요한 정도와 실제 GPU 결과로 판단한다.
- **입력:** 장식의 Raycast Target을 끄고, 조작 부품에만 입력을 연결한다.
- **측정:** 대표 화면과 다수 주문/다인 선택 상태에서 CPU·GPU 프레임 시간, UI 재빌드, 배치/드로콜, GC, 텍스처/RenderTexture 메모리와 로딩을 확인한다. 측정 전 성능 수치를 보장하거나 불필요한 최적화 구조를 추가하지 않는다.

## 5. 전체 적용 순서

1. 기준 화면·부품 명세 및 서체/재질 샘플. 공통 클립보드의 두 규격과 2D/3D 표시 방식을 먼저 검증.
2. 대표 낮 화면: HUD + 주문 + 제조 + 판정.
3. 밤 화면: HUD + 가방 + 스킬 + 루팅 + 귀환 안내.
4. 캐릭터·팀 선택: 다인 무대와 선택·준비 상태.
5. 타이틀·방 목록·보조 대기실.
6. 정산·최종 결과·설정·로딩·페이즈 전환과 나머지 공통 부품.
7. 전체 화면 간 재질·크기·레이어·입력·수명과 실제 빌드 검증.

대표 화면에서 맞춘 부품 규격과 렌더링 방식을 뒤 단계에 공유한다. 각 단계마다 Unity 캡처와 기준 시안을 대조해 차이를 수정한다.

## 6. 검증과 완료 판정

### 외형

- 기준 해상도에서 위치·크기·여백·실루엣·색·재질·그림자·글자 인상이 시안과 맞는가.
- 투명 가장자리·9-slice 모서리·작은 아이콘과 숫자가 깨끗한가.
- UI를 실제 카메라·배경 위에서 봤을 때 가독성과 원래의 루이지 느낌을 함께 유지하는가.
- 비교판에만 있던 설명/다중 상태가 상시 HUD에 섞여 들어가지 않았는가.

### 동작

- 실제 매출·시간·적재량·인내심·재료·판정·선택·준비 상태와 연결되는가.
- 낮/밤 전환, 상자 닫기, 뒤로 가기, 팝업 중 입력, 화면 재진입이 정상인가.
- 긴 이름·큰 수치·빈 상태·가득 참·분실·실패 상태가 잘리거나 겹치지 않는가.
- 1/2/4/8인 팀 선택과 호스트·클라이언트에서 표시가 올바른가.

### 해상도와 성능

- 1080p 기준 대조 후 1440p·울트라와이드에서 앵커·크기·잘림을 확인한다.
- 텍스처/아틀라스·마스크·머티리얼·갱신되는 Canvas를 실제 프로파일링하고 필요한 범위만 조정한다.
- 빌드에서 폰트 글리프·스프라이트 참조·Addressables 로딩을 확인한다.

컴파일 통과·프리팹 파일 생성만으로 완료하지 않는다. 실제 게임 캡처의 시안 재현과 실제 상태 동작을 모두 확인해 완료한다. 아직 재현되지 않은 항목은 별도 목록에 남긴다.

## 작업 방법과 계획 검토에 사용한 스킬

계획은 `ui-ugui`, `optimize-text-mesh-pro`, `unity-architecture`, `unity-cli` 지침과 실제 프로젝트 파일을 참고했다. `graphify` 도구는 현재 연결되지 않아 직접 파일을 확인했다. 구현 단계의 에디터 조작·프리팹 배선·캡처는 Unity CLI로 수행한다. 이번에는 에디터 실행·플레이 모드·빌드 검증을 수행하지 않았다.
