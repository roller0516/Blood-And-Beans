# BLOOD & BEAN — 코드 설계 / 스크립트 구조

> 기획서 v2.5 기준. Unity 6000.5.9f1 · URP · 3D 탑다운 · Netcode for GameObjects 2.13.1
>
> 파일 상태는 실제 `BloodAndBeans/Assets/Scripts` 기준이다. "예정"은 아직 파일이 없는 것이고, 폴더는 첫 파일이 생길 때 만든다.

---

## 1. 설계 축 3개

**① 페이즈 경계가 곧 폴더 경계다.** 기획서가 낮과 밤을 갈라놨고, 실제로 박스 로직은 커피 머신을 알 필요가 없다. 밤 로직은 낮 설비를, 낮 로직은 안개·박스를 모른다. 양쪽이 같은 걸 필요로 하면 `Core/`로 올린다 — 이게 유일한 승격 경로다.

`Day/` → `Night/` 참조는 코드에 0건이다. 반대로 **`Day/Cafe`만은 다른 폴더가 들어와서 읽는다** — 팀을 알아내는 유일한 앵커라서다.

| 들어오는 곳 | 왜 |
|---|---|
| `Night/ReturnZone` → `Cafe.Of()` | 귀환 지점이 카페의 자식이라 소속 팀을 부모에서 읽는다 |
| `Player/PlayerTeam` → `Cafe` 개수 | 팀 수를 씬의 카페 수로 센다 |
| `Economy/SaleRegister`·`TransitionLedger` → `Cafe` | till·설비·그릇을 팀별로 찾는다 |

`Cafe`는 이제 "낮의 카페"가 아니라 사실상 **팀 앵커**다. 팀 조회(`TeamId`, `Of()`)를 `Core/`로 올리고 `Day/Cafe`에는 낮 설비 참조만 남기는 것이 정리 방향이다. 지금 당장 급하지 않은 이유: 방향이 한쪽(→ `Cafe`)뿐이라 순환이 없다.

**② 서버가 정하고 클라이언트는 읽는다.** 상태 변경 진입점은 전부 `[Rpc(SendTo.Server)]`이고, 결과는 `NetworkVariable`/`NetworkList`로 복제된다. 클라이언트가 직접 쓰는 게임 상태는 없다. 밤은 자원 선착순 경쟁이라 클라이언트에게 판정을 맡길 수 없고, 낮의 매출은 승리 지표라 더욱 그렇다.

**③ 계산은 순수 함수로 빼서 씬 없이 검증한다.** 이제 이건 관습이 아니라 어셈블리 경계다 — `Rules/`가 `BB.Rules`이고 `noEngineReferences: true`라, 규칙에 `UnityEngine`을 들이면 컴파일이 깨진다. `BB.Tests.EditMode`가 `BB.Rules`만 참조해 기획서 표와 값을 직접 대조한다(40건).

## 2. 의존 방향

실제 참조 간선은 이게 전부다.

| 화살표 | 무엇을 위해 |
|---|---|
| 전부 → `Rules/` | 재료·메뉴·가격·임대료·홀드·무게. `BB.Rules`는 엔진조차 참조하지 않는다 |
| 전부 → `Core/` | 페이즈 루프, 카메라, 팀 시야. `Core/`는 `Rules/` 외에 아무것도 참조하지 않는다 |
| `Night/` → `Economy/` | `Penalties` 조회 (시야·개봉·무게 페널티) |
| `Day/` → `Economy/` | `Penalties` 조회 (제작 속도·머신·그릇 페널티) |
| `Economy/` → `Day/` | 팀별 till·설비·그릇·손님줄 찾기 |
| `Night/` → `Day/Cafe` | 귀환 지점의 소속 팀 |
| `Player/` → `Day/Cafe` | 팀 수 |
| `UI/` → 전부 | 읽기만. 상태 소유 없음 |

- 매출은 `Day/`가 계산하지 않는다. `CustomerQueue.Served` 이벤트만 던지고 `Economy/SaleRegister`가 구독한다 — 그래서 `Day/`에는 `Economy/`를 향한 매출 참조가 없다.
- **`Day/` ↔ `Economy/`는 폴더 단위로 양방향이다.** `Penalties`가 낮·밤 양쪽 규칙이라 어느 쪽에 둬도 반대 화살표가 생긴다. 둘 다 `BB.Game` 안이라 컴파일에는 문제가 없고, `Penalties`가 `MatchDirector`로 들어가면 사라진다(아키텍처_v1.0.md §2.2).
- **`Day/` → `Player/`가 생겼다.** `CompletionGauge`와 `Cafe.SameTeamServer`가 발신자의 팀을 알아야 해서다. 팀 조회는 `PlayerTeam.Of/Local` 한 쌍뿐이고, 4단계에서 `MatchDirector`로 올라간다.

## 3. 폴더별 파일

### Core/

밤낮 공통 뼈대. 여기 있는 건 페이즈를 모른다.

| `MatchDirector.cs` | 있음 | **팀의 유일한 원천.** 팀 슬롯(카페·안개) 주입, 좌석 배정, 팀별 `TeamLedger` 보유. 런타임 카페는 NGO 씬 처리가 끝난 `sceneLoaded` 이후 서버가 스폰 | 3장, 10장 |
| `GamePhase.cs` | 있음 | 밤→전환→낮 루프, 서버 권한, 종료 시각만 동기화. `PhaseEntered`는 인스턴스 이벤트 | 4장 |
| `TeamVision.cs` | 있음 | 카메라 컬링으로 남의 카페를 가린다 | 3.1 |
| `TopDownCamera.cs` | 있음 | 탑다운 추적 카메라 | 12장 |
| `NetworkAutoStart.cs` | 있음 | 메인 에디터=Host, 가상 플레이어=Client 자동 접속 | — (개발 편의) |
| `NetworkHud.cs` | 있음 | Host/Client/Server 수동 버튼 | — (개발 편의) |

`NetworkAutoStart`와 `NetworkHud`는 출시 전에 뺀다. `TeamVision`은 렌더링만 막는다 — 복제 자체를 막는 게 아니므로, 남의 카페 내부를 진짜로 감춰야 하면 복제 범위로 다시 풀어야 한다.

`TeamRegistry`는 만들지 않았다. 팀은 `Cafe.TeamId`와 `PlayerTeam.Team`으로 충분하다. 로비가 생겨 팀 구성을 사람이 정하게 되면 그때 만든다.

### Rules/ — `BB.Rules`

**이 폴더가 코어다.** UnityEngine을 참조하지 않는다(`noEngineReferences: true`). 그래서 씬도
플레이모드도 없이 전량 테스트되고, 엔진 타입이 규칙에 스며드는 것이 컴파일러로 막힌다.

|---|---|---|---|
| `Ingredients.cs` | 있음 | 재료 enum + 무게 테이블 + `IsStaple` (상비 재료 판정의 유일한 원천) | 7.1 |
| `MenuDef.cs` | 있음 | 메뉴를 태그 조합으로 정의(`Menus.All`, `Match`, `TagsOf`). 손님은 메뉴 이름을 모른다 | 7.2 |
| `SalePrice.cs` | 있음 | 최종 판매가 계산식. 상태 없는 static | 5.6.2 |
| `Rent.cs` | 있음 | 일차별 임대료, 부채 이월, 미납 연속 카운트 | 3.2 |
| `Forecast.cs` | 있음 | 다음 날 손님 구성 + 인기 재료 2~3종 선정 | 5.5, 5.6 |

`Assets/Tests/EditMode`(`BB.Tests.EditMode`)가 **`BB.Rules`만** 참조한다. 규칙을 검증하는 데
게임 어셈블리가 필요하다면 그 규칙은 아직 규칙이 아니라는 뜻이다.

`Penalties`는 여기 없다. 팀별 mutable static이라 순수 규칙이 아니고, `MatchDirector`로
들어가는 것이 정해진 경로다(아키텍처_v1.0.md §2.2).

`Penalties`는 삭제했다. 페널티는 낮·밤 양쪽에 걸치므로 `Day/`나 `Night/` 어느 쪽에도 둘 수 없었고, 그래서 static이었다. 이제 `Rules/TeamLedger`가 그 표를 들고 `MatchDirector`가 팀별로 소유한다 — 양쪽 폴더가 director 하나만 보면 되고, 판이 끝나면 원장도 같이 사라진다.

타이틀은 별도 Model을 복제하지 않는다. 영속 `SteamLobby`가 Model이고 `TitlePresenter`가
상태 변경을 한 번 구독해 `TitleScreen`에 표시할 값만 전달한다. 세 페이지는 동시에 하나만
활성화되는 Screen이며, 닫은 뒤 같은 Screen으로 돌아오는 `BoxWindow`·확인창은 Popup으로 둔다.

**HUD는 파일 하나다.** `PhaseHud`, `RankTicker`, `ForecastPanel`, `LoadGauge`를 따로 두려 했지만 넷은 같은 uGUI 출력에서 페이즈로 분기되는 읽기 전용 표시일 뿐이고 상태를 소유하지 않는다. 스킨·입력·애니메이션이 붙어 변경 이유가 갈리면 그때 쪼갠다.

## 4. 상태 소유권

누가 진실의 원천인지가 흐려지면 서버·클라가 각자 계산하기 시작한다. 아래가 전부다.

| 상태 | 소유 | 복제 방식 |
|---|---|---|
| 페이즈·일차·종료 시각 | `GamePhase` | `NetworkVariable` 4개. **종료 시각만 보내고 남은 시간은 클라가 계산** |
| 안개 걷힌 셀 | `FogOfWar` (팀별 인스턴스) | `NetworkList<int>` 셀 인덱스 |
| 박스 내용·개봉·공개 시각 | `ItemBox` | `NetworkList<int>` + `NetworkVariable`. 내용 롤은 서버 |
| 적재량·소지품 | `PlayerInventory` | `NetworkList<int>` + `NetworkVariable<float>` |
| 설비 상태·투입 재료 | `Station` | `NetworkVariable<StationState>` + `NetworkList<int>` |
| 완성 게이지 | `CompletionGauge` | 활성 여부 + 시작 시각. 침 위치는 서버 시계로 양쪽이 같이 계산 |
| 손님 인내심·주문 태그 | `Customer` | `NetworkVariable` 7개 |
| 그릇 | `Dish` | clean/dirty 2개 (InUse는 파생값) |
| 누적 매출 | `Scoreboard` | `NetworkList<int>`. 팀 수 = 씬의 till 수 |
| 임대료·부채·예보 원본 | `TransitionLedger` | 복제하지 않음. 표시용 요약만 RPC로 |
| 손에 든 것 | `Hands` static 맵 | 복제하지 않음 (위 Day/ 항목 참조) |

**연속값은 RPC로 흘리지 않는다.** 타이머는 종료 시각, 게이지 침은 시작 시각, 위치는 NetworkTransform. 매 프레임 RPC는 없다.

## 5. 호출 경로

**낮 — 한 잔이 돈이 되기까지**

```
IngredientShelf.TakeRpc → Hands.GiveIngredient
  → Station.UseRpc (재료 투입, Dish.ClaimServer로 그릇 점유)
  → Station.UseRpc (빈손) → Cooking → CompletionGauge.BeginServer
  → CompletionGauge.StopRpc → Judgement → HeldItem(Product)
  → Counter.ServeRpc → CustomerQueue.TryServeServer
  → event Served(ServeInfo) → SaleRegister.Book
  → SalePrice.Calculate → Scoreboard.AddSale
```

`Day/`는 `Economy/`를 모른다. 경계는 `Served` 이벤트 한 줄이다.

**밤 — 한 사이클**

```
GamePhase.Enter(Night) → static PhaseEntered
  ├ FogOfWar : 걷힌 셀 초기화 (매 밤)
  └ ItemBox  : 임시 더미 디스폰
PlayerInteract.HoldBeginRpc → ItemBox.BeginHoldServer
  → (서버 Update) ItemBox.Tick → 개봉 / TakeOne → PlayerInventory.AddServer
DashHarass.DashRpc → 적재 80%↑ → DropShareServer → DroppedPile(ItemBox 재사용)
GamePhase.Enter(Transition) → PhaseEntered → ReturnZone.Settle
                            → 미귀환자 LoseHalfServer, 잔량 → TeamStock.DepositServer
                            → TransitionLedger : 임대료·페널티·예보
```

**페이즈 경계는 각자 폴링하지 않는다.** `GamePhase.PhaseEntered` 하나를 구독한다. 두 컴포넌트가 같은 경계를 따로 감시하다 안개 초기화가 조용히 멈춘 적이 있어 이렇게 고정했다.

## 6. 팀 스코프는 탐색이 아니라 부모로 해결한다

- `Cafe.Of(component)`가 부모를 타고 올라가 소유 카페를 찾는다. 카페를 복제하면 설비·till·귀환 지점·손님줄이 자동으로 자기 팀에 붙는다.
- `FogOfWar.ForTeam(team)`이 팀별 안개를, `TeamVision`이 카메라 컬링으로 남의 카페를 가린다.
- **전역 탐색(`FindFirstObjectByType`)은 씬에 하나뿐인 것에만 쓴다** — `GamePhase`, `Scoreboard`. 팀별 객체에 그걸 쓴 것이 QA의 B4·D2·B3 결함 원인이었다(한쪽 팀만 예보를 받고, 한쪽 귀환 지점이 남의 팀을 판정했다).
- 새 싱글턴을 만들지 않는다. `CustomerQueue.Instance`는 읽는 곳이 없고 카페가 둘이라 마지막 `Awake`가 이기는 구조여서 삭제했다.
- 예외는 `Penalties`(팀별 static)와 `Hands`(clientId별 static) 둘뿐이고, 둘 다 이유와 초기화 지점이 위에 적혀 있다.

## 9. 검증 방식

- **순수 로직**: `SalePriceSelfCheck`처럼 씬 없이 돌리고, 기획서 표와 값을 직접 대조한다.
- **생명주기·네트워크**: Host + MPPM 가상 클라이언트로 실제 페이즈를 돌려 콘솔·상태를 확인한다. 팀 분리 결함은 두 팀을 동시에 띄우지 않으면 드러나지 않는다.
- 결함은 `qa-final.md`에 id·판정·근거로 남긴다. 근거는 관찰한 값이어야 하고, 실행하지 못한 검증은 실행한 것처럼 적지 않는다.
- 페이즈 길이를 임시로 줄여 검증했다면 **원래 값으로 되돌리고 디스크에서 확인**한다.
