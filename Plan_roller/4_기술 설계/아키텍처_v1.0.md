## 1. 진단 — 지금 구조가 서비스에서 깨지는 지점

프로토타입으로서는 코어 루프가 돈다. 아래는 "이대로 키우면 반드시 터지는 것"만 골랐고, 전부 파일에서 확인했다.

### 1.1 해결 — 홀드 시간은 서버가 판정한다

`Core/HoldTimer.cs`가 서버 시간으로 플레이어별 홀드를 누적하고, `Night/PlayerInteract.cs`는 눌림·뗌만 서버에 보고한다. `Night/ItemBox.cs`와 `Day/Sink.cs`는 서버에서 거리·팀·상태와 경과 시간을 다시 검증한다. 클라이언트가 RPC를 일찍 보내도 완료되지 않는다.

`Core/HoldTimerSelfCheck.cs`가 조기 완료 거부, 정시 완료, 취소, 플레이어 간 격리를 수동 검증한다. 이 검사는 이후 EditMode 테스트로 승격한다.

### 1.2 해결 — 완성 게이지는 팀별로 격리된다

`Day/CompletionGauge.cs`는 로컬 플레이어 팀의 게이지만 선택하고, 서버 RPC에서도 `RpcParams.Receive.SenderClientId`로 발신자의 팀과 거리를 다시 검증한다. 카페 A의 플레이어가 카페 B의 게이지를 멈출 수 없다.

### 1.3 구조 — 권위 상태와 입력·표현이 같은 클래스에 있다

`Day/Station.cs`는 한 클래스에서 `NetworkVariable`을 소유하고(`:63-67`), `Keyboard.current`를 읽고(`:97`), `OnGUI`로 그린다(`:189`). 같은 패턴이 `Counter`, `Sink`, `IngredientShelf`, `CompletionGauge`, `PlayerInteract`, `Dish`, `CustomerQueue`, `PhaseHud` — 총 9곳.

리슨 서버에서는 Host 프로세스가 로컬 입력과 서버 권위를 동시에 가진다. 이 둘이 같은 클래스에 있으면 로컬 Host 전용 경로가 권위 검증을 우회하기 쉽고, 클라이언트 전용 표현 변경이 서버 규칙까지 흔든다. 따라서 전용 서버를 만들지 않더라도 분리한다.

부수 효과로 `.inputactions` 에셋(`Assets/InputSystem_Actions.inputactions`)이 **한 곳에서도 참조되지 않는다.** 리바인딩·게임패드·플랫폼 키 차이를 지금 구조로는 지원할 수 없고, 키가 8개 파일에 하드코딩돼 있다.

### 1.4 해결 — 팀의 원천은 `MatchDirector` 하나다

여섯 곳이 각자 답하던 질문(씬 직렬화 `teamId` 2곳, `OwnerClientId % 카페 수`, `Cafe` 개수, till 개수, 그 개수의 재사용)을 `Core/MatchDirector.cs` 하나로 모았다. 팀 id는 **슬롯 배열의 인덱스**이고, `Cafe`와 `FogOfWar`는 자기 팀을 **주입받는다**. `Cafe.teamId`와 `FogOfWar.teamId`의 `[SerializeField]`는 제거했다.

슬롯 배열은 씬 데이터라 모든 피어에서 동일하다. 그래서 `MatchDirector`는 NetworkBehaviour가 아니고, 팀 id를 복제하지 않고 각자 Awake에서 같은 답을 계산한다. 서버에만 있는 것은 팀별 `TeamLedger`와 좌석 카운터뿐이다.

미해결로 남은 것: 로비가 없어 **2인 1팀을 사람이 짤 수 없다.** 좌석 배정은 접속 순서 라운드로빈이고, 기획서 10장이 요구하는 로비는 §5 8단계다.

### 1.5 해결 — 판을 넘어 사는 static 상태를 없앴다

다섯 개가 전부 사라졌다. 남은 static은 조회 헬퍼(`PlayerTeam.Of/Local`, `PlayerCarry.Of`, `Cafe.Of/SameTeamServer`, `MatchDirector.Find`)뿐이고, 이들은 상태를 들고 있지 않는다.

| 사라진 static | 어디로 갔나 |
|---|---|
| `Hands` (`clientId → HeldItem`) | `Player/PlayerCarry` 컴포넌트. 플레이어와 함께 파괴된다 — 나간 클라이언트의 컵이 맵에 영원히 남던 문제가 닫혔다 |
| `Penalties.ByTeam` | `Rules/TeamLedger`. `MatchDirector`가 판마다 새로 만든다 |
| `FogOfWar.All` | `MatchDirector.FogOf(team)`. "없으면 첫 번째 것" 폴백이 사라져 잘못된 팀의 안개를 줄 수 없다 |
| `CompletionGauge.Live` | `Cafe.Gauges`. 후보 집합이 애초에 자기 카페 것뿐이라 필터를 잊을 수 없다 |
| `GamePhase.PhaseEntered` (static event) | 인스턴스 이벤트. 구독자는 `MatchDirector.Phase`로 접근한다 |

`TransitionLedger`의 `Penalties.ResetServer()` 우회도 함께 삭제했다. 지울 static이 없으면 지우는 코드도 필요 없다.

### 1.6 성능 — 매 프레임 전역 탐색

- `Night/PlayerInteract.cs:46` — **플레이어마다 매 프레임** `FindObjectsByType<ItemBox>()`. 숲 박스가 수십 개, 인원이 8명이면 프레임당 수백 회 순회 + 배열 할당.
- `Night/FogOfWar.cs:105`, `Night/ReturnZone.cs:26` — `Update`에서 매 프레임 `FindFirstObjectByType<GamePhase>()`.
- `Core/TopDownCamera.cs:27`, `Player/PlayerTeam.cs:16` — 초기화 경로라 상대적으로 덜 급하다.

AGENTS.md가 금지한 패턴이고, 프로파일 없이도 성격이 분명한 낭비다.

### 1.7 운영 — 없어서 서비스가 안 되는 것

씬 1개(`Scenes/SampleScene.unity`), 로비 없음, 연결 승인 없음, Host 종료 처리 없음, 밸런스 테이블 0개(코드 내 `ponytail:` 자리표), 텔레메트리 없음. Steam Lobby는 의도적으로 보류하지만, 그 전에도 직접 연결 세션의 참가 검증과 판 종료 처리는 필요하다.

어셈블리와 검증은 3단계에서 세웠다: `BB.Rules`·`BB.Game`·`BB.Tests.EditMode` 3개, EditMode 테스트 40건, `.github/workflows/editmode-tests.yml`. 수동 실행이던 셀프체크 2종은 테스트로 흡수하고 삭제했다. **CI 워크플로는 아직 GitHub에서 실행된 적이 없다** — Unity 라이선스 시크릿 등록과 game-ci의 `6000.5.9f1` 이미지 존재 확인이 남아 있다.

## 2. 목표 아키텍처

### 2.1 레이어 — 어셈블리 4개

```
BB.Boot        조립 루트 · 씬 플로우 · 세션/로비 · Host/Client 시작점
   │  (참조: 전부)
   ├── BB.Client      입력 · UI · 렌더 · 사운드 · 카메라
   │       │
   └── BB.Game        Host 서버 권위 게임플레이 (NetworkBehaviour)
           │
           ├── BB.Data     ScriptableObject 밸런스 테이블
           └── BB.Rules    순수 C# 규칙 (UnityEngine 참조 0)
```

- **`BB.Rules`가 이 게임의 코어다.** 판매가, 임대료·부채, 예보 4규칙, 무게 밴드, 메뉴 태그 대조, 페이즈 순환 표. UnityEngine을 참조하지 않으므로 씬·플레이모드 없이 전량 테스트된다. 이미 `SalePrice`, `Rent`, `Forecast`, `Menus`, `Ingredients`, `PlayerInventory.SpeedMultiplier`가 사실상 이 성질을 갖고 있다 — 옮기기만 하면 된다.
- **`BB.Game`은 `BB.Client`를 참조하지 않는다.** Host 한 프로세스 안에서도 서버 규칙이 로컬 입력·UI를 신뢰하지 않게 만드는 경계다.
- **`BB.Data`는 규칙을 담지 않는다.** SO는 값만 들고 있고, 계산은 `BB.Rules`가 POCO 스냅샷을 받아서 한다. 그래서 테스트가 SO 에셋을 로드하지 않는다.
- `BB.Boot`만 씬·NetworkManager·세션을 안다. 게임플레이가 `NetworkManager.Singleton`을 직접 뒤지는 코드는 여기로 모은다.

**`BB.Rules`와 `BB.Game`은 만들었다.** `Assets/Scripts/Rules/`가 `BB.Rules`(`noEngineReferences: true`)이고 나머지 `Assets/Scripts/`가 `BB.Game`이다. `BB.Rules`에는 `SalePrice`·`Rent`·`Forecast`·`Menus`·`Ingredients`·`HoldTimer`·`LoadBands`가 있고, 테스트 어셈블리는 `BB.Rules`만 참조한다 — 규칙을 검증하는 데 엔진이 필요 없다는 것이 컴파일러로 강제된다.

`BB.Client` 분리는 입력·표현을 실제로 옮기는 단계(§5 5~6단계), `BB.Data` 분리는 7단계에서 한다. 어셈블리를 미리 4개로 쪼개는 것 자체가 목적이 아니다.

폴더는 지금의 페이즈 경계(`Core/ Day/ Night/ Economy/ Player/ UI/`)를 유지한다. 잘 서 있고, 어셈블리 경계와 직교한다.

### 2.2 코어 — 상태 소유권

한 판의 권위 상태를 소유하는 것은 **`MatchDirector`(서버, 씬에 1개)** 하나다. 지금 `GamePhase`·`Scoreboard`·`TransitionLedger`·`Penalties`(static)에 흩어진 "판 단위" 상태를 여기로 모은다.

```
MatchDirector (server)
├─ Phase / Day / EndsAt          ← GamePhase 흡수
├─ TeamRoster[]                  ← 세션에서 받은 팀 편성 (신설)
└─ TeamLedger[team]              ← 팀 단위 상태를 배열 하나로
     ├─ Revenue                       ← Scoreboard
     ├─ Rent (Debt / MissStreak)      ← TransitionLedger
     ├─ Penalty                       ← Penalties (static 제거)
     └─ Stock                         ← 밤에 캔 재료 (§3, 신설)
```

- **팀 인덱스가 유일한 키다.** `Cafe`, `FogOfWar`, `ReturnZone`, `SaleRegister`는 `teamId`를 직렬화하지 않고 **`MatchDirector`가 시작 시 슬롯에 주입한다.** 씬은 "카페 슬롯 4개"만 갖고, 세션이 팀 수만큼 활성화한다.
- `Penalties`·`Hands`의 static은 각각 `TeamLedger`와 `PlayerCarry`(플레이어 컴포넌트)로 들어간다. static 두 개가 사라지면 판 경계 초기화 코드도 같이 사라진다.
- `GamePhase.PhaseEntered`는 static event를 버리고 `MatchDirector`의 인스턴스 이벤트가 된다. 구독자는 `MatchDirector`를 직렬화 참조로 받는다(`CustomerQueue`가 이미 `GamePhase`를 그렇게 받고 있다 — `Day/CustomerQueue.cs:29`).
- **연속값은 계속 보내지 않는다.** 종료 시각·시작 시각만 복제하고 남은 시간은 클라가 계산하는 현재 패턴(`GamePhase.Remaining`, `CompletionGauge.Needle`)은 옳다. 유지한다.

### 2.3 코어 — 상호작용 경로 하나

낮의 F 한 키가 설비마다 다른 뜻을 갖는 것은 기획(11장)이고, 그 분기는 서버에만 있어야 한다. 지금은 설비 6종이 각자 근접 판정 + 입력 감시 + RPC + OnGUI를 복제한다.

```
[BB.Client] PlayerInputRouter (owner only)
      InputActions: Move / Interact(hold) / Dash / Dump
                     │  Interact 눌림·뗌만 전달
                     ▼
[BB.Game]   PlayerInteractor (NetworkBehaviour, owner→server)
      InteractBeginRpc(targetNetworkObjectId)
      InteractEndRpc()
                     │  서버가: 대상 유효성 · 거리 · 팀 · 홀드 시간 판정
                     ▼
[BB.Game]   IInteractable (Station / Counter / Sink / Shelf / ItemBox / Gauge)
      ServerBegin(clientId) → 필요 홀드 시간 반환
      ServerComplete(clientId)
      ServerCancel(clientId)
```

- **홀드 시간은 서버가 잰다.** 클라이언트는 "누르기 시작함 / 뗌"만 보낸다. §1.1과 §1.6이 동시에 해결된다.
- 대상 선택도 서버가 검증한다. 클라이언트는 자기가 조준한 대상의 id를 보내고, 서버가 거리·팀·상태를 다시 본다.
- `IInteractable`은 구현이 6개 있으므로 만든다. 구현 1개짜리 인터페이스는 만들지 않는다.
- 근접 대상 탐색은 `FindObjectsByType` 대신 **트리거 콜라이더 진입/이탈로 후보 집합을 유지**한다. 프레임당 전역 순회가 사라진다.
- `OnGUI` 9곳은 전부 `BB.Client`의 uGUI로 옮긴다. 게임플레이 컴포넌트는 읽기 전용 프로퍼티만 노출하고 그리지 않는다.

### 2.4 넷코드

| 항목 | 결정 |
|---|---|
| 토폴로지 | **리슨 서버 방식의 클라이언트-서버. NGO Host가 단독 권위**이며 Distributed Authority는 쓰지 않는다. 네트워크 경로가 P2P여도 게임 상태 권위는 Host 한 곳에 있다 |
| 세션 | Steam Lobby 소유자 또는 선정된 멤버가 NGO Host를 시작하고 자기 로컬 클라이언트도 함께 실행한다. 나머지는 NGO Client로 참가한다 |
| 개발 연결 | Steam SDK 없이 Unity Transport 직접 IP + MPPM. 현재 프로토타입의 `NetworkAutoStart`/`NetworkHud`를 개발용으로만 사용한다 |
| 서비스 연결 | **Steam Lobby = 방 탐색·초대·멤버 메타데이터**, **Steam P2P/SDR = 패킷 전송**, **NGO = 복제·RPC·스폰·권위 규칙**. Steam 전송 계층은 NGO 2.13 호환성을 확인한 어댑터 하나로 `SessionLauncher` 뒤에 둔다 |
| 비용 | 전용 게임 서버를 운영하지 않으므로 게임 서버 호스팅 비용 목표는 0원. Steamworks 계약·수수료·개발/운영 인건비까지 0원이라는 뜻은 아니다 |
| Host 종료 | 초기 서비스는 **Host migration 없음**. Host가 나가거나 연결이 끊기면 매치를 종료하고 결과 저장 없이 로비로 복귀한다 |
| 신뢰 한계 | 원격 클라이언트 조작은 Host가 검증하지만 Host 사용자는 자기 프로세스를 변조할 수 있다. 경쟁성·치트 신고가 실제 서비스 문제로 확인될 때만 전용 서버를 재검토한다 |
| 이동 | **서버 권위.** 입력 벡터를 RPC로 보내고 서버가 `Rigidbody`를 움직인다. NetworkTransform은 서버 권위 모드. 예측 없음 |
| 대시 견제 | 이미 서버가 피해자·낙하·경직을 결정한다(`Night/DashHarass.cs:42-66`). 넉백 적용만 `SendTo.Owner`로 클라에 위임돼 있는데(`:68`), 이동이 서버 권위가 되면 서버에서 그대로 적용한다 |
| 복제 범위 | 남의 카페 설비·손님·인벤토리는 `NetworkShow/Hide`로 **복제를 끊는다.** `Core/TeamVision.cs`의 카메라 컬링은 그때까지의 임시 수단 |
| 물리 | 카페·숲 모두 서버에서만 시뮬레이션. 클라이언트 물리는 표현용 |
| 손님 스폰 | 서버. 현재 판당 `Instantiate`+`Spawn`/`Despawn`(`Day/CustomerQueue.cs:76-84`)이며, 8인 4팀에서 수치를 보고 필요하면 `INetworkPrefabInstanceHandler` 풀로 바꾼다. 프로파일 전에는 하지 않는다 |
| 버전 게이트 | 접속 시 프로토콜 버전 + `BalanceSet` 해시 일치 검사. 불일치는 거부 |

NGO 2.13에서 실제로 쓸 API(`NetworkShow/Hide`, NetworkTransform 권위 모드, `INetworkPrefabInstanceHandler`)와 Steam 전송 어댑터는 **구현 착수 시점에 설치된 패키지 소스와 호환 표를 확인한 뒤** 쓴다. 현재는 Steam SDK·Steam Lobby·Steam 전송 패키지를 추가하지 않는다.

### 2.5 씬 · 세션 플로우

```
[현재 프로토타입]
Boot/Dev Connect  ── StartHost 또는 직접 IP StartClient
       ↓ NetworkSceneManager
Match              Forest(단일 월드) + Cafe 슬롯 4개
       ↓
Result              최종 순위 → Dev Connect

[Steam 통합 후]
Steam Init → Steam Lobby(초대·팀 편성·맵 선택)
       ↓ Lobby Owner가 NGO Host 시작 / 멤버는 Client 참가
Match  ── Steam P2P/SDR 전송, NGO Host 권위
       ↓
Result ── 판 텔레메트리 → Steam Lobby
```

- 씬 이름 `SampleScene`은 `Match_Forest`로 바꾼다. URP 템플릿 기본값이 남아 있고, 기획서 10장이 맵 복수를 예정한다.
- 개발 편의용 `Core/NetworkAutoStart.cs`, `Core/NetworkHud.cs`는 `BB.Client`의 에디터 전용 경로로 옮기거나 `Boot`의 개발 모드 플래그 뒤로 넣는다. 출시 빌드에 남기지 않는다.
- `SessionLauncher`는 `StartHost`/`StartClient`와 연결 수명만 소유한다. 현재는 직접 IP 구현 하나만 두고, Steam 통합 때 전송 설정과 Lobby 메타데이터 해석을 이 조립 지점에 추가한다.
- Steam Lobby가 들어오기 전의 팀 편성은 개발용 슬롯/접속 순서로 제한한다. 이 임시 규칙을 게임플레이 여러 곳으로 퍼뜨리지 않고 `MatchDirector`의 팀 명단 입력 한 곳으로 모은다.

- 코드 내 자리표 34곳이 여기로 모인다. `Economy/Rent.cs:10`의 임대료 배열, `Core/MenuDef.cs:38-49`의 가격, `Core/Ingredients.cs:14-26`의 무게, `Day/Customer.cs:33-45`의 인내심·가격 가중, `Night/ItemBox.cs:117-133`의 등급별 롤이 대표다.

- `BalanceSet`은 판 시작 시 해시를 계산해 클라이언트에 내려보내고, 클라이언트가 자기 해시와 비교한다. 다르면 접속을 끊는다. 밸런스 불일치가 "왜 저쪽만 비싸게 파나"로 나타나는 것을 막는다.

### 2.8 텔레메트리 · 운영

판 종료 시 NGO Host가 JSON 1건을 남긴다. 이것 없이 기획서 14장의 15개 미결 수치를 잡을 방법이 없다.

```
match{ id, balanceHash, mapId, teams, days, durationSec }
team[]{ revenuePerDay[], rentPaid[], missStreakMax, upgrades[] }
night[]{ boxesOpened{tier1,2,3}, itemsTaken, dashHits, spills, returnedOnTime, peakLoadRatio }
day[]{  served, left, gauge{perfect,good,miss,burnt}, dishStarvedSec }
```

읽는 값은 정해져 있다. 임대료 미납률(3.2 곡선이 맞는가), 미귀환률(밤 2분이 맞는가), 등급별 개봉 수(6.5.2 분포가 맞는가), Burnt 비율(게이지 10초가 맞는가), `dishStarvedSec`(그릇 4개가 맞는가).

수집은 우선 **Host 로컬 파일**로 시작한다. Host 변조·누락 가능성이 있으므로 운영 지표의 참고 자료로만 쓰고, 신뢰 가능한 전적이 필요해질 때 백엔드를 별도 검토한다.

## 3. 코어 루프 — 현재 닫힌 상태

현재 구현은 다음 흐름으로 기획서의 밤→낮 고리를 닫았다.

```
밤: ItemBox → PlayerInventory
   → ReturnZone 정산(미귀환자는 50% 소실)
   → 카페별 TeamStock 적립
낮: IngredientShelf → 기본 재료는 무한 공급
                    → 채집 재료는 TeamStock에서 차감, 없으면 지급 거부
```

`Economy/TransitionLedger.HeldByTeams()`도 실제 카페별 `TeamStock`을 읽어 다음 날 주문 예보에 반영한다. `TeamStock`은 현재 구조를 살린 과도기 구현이며, §2.2의 `MatchDirector/TeamLedger` 단계에서 판 단위 상태와 함께 합친다. 그 전에는 같은 재고 계층을 하나 더 만들지 않는다.

## 5. 실행 순서

각 단계는 앞 단계 없이는 검증이 안 되는 순서로 놨다. 단계마다 "끝났다"의 기준을 붙였다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **1 (완료)** | **코어 루프 닫기** — `TeamStock` + `ReturnZone` 정산 적립 + `IngredientShelf` 재고 차감 | 밤에 못 캔 채집 재료는 낮에 꺼낼 수 없다 |
| **2 (완료)** | **신뢰 경계 보완** — 게이지 팀 격리, 홀드 서버 판정, 낮 설비 RPC의 발신자 ID 사용 | 다른 팀 설비 조작과 clientId 위조가 거부되고, 클라 시간 조작으로 즉시 완료 불가 |
| **3 (완료 · CI 미실행)** | **`BB.Rules` 분리 + EditMode 테스트 + CI** | 씬 없이 규칙 40건이 로컬에서 녹색. 워크플로는 작성했으나 시크릿 미등록으로 아직 GitHub에서 안 돌았다 |
| **4 (완료)** | **팀 원천 단일화** — `MatchDirector` + `TeamLedger`, static 5개 제거, 씬 직렬화 `teamId` 제거 | 팀 수를 세는 곳이 1곳. Host+Client 2인 세션에서 팀 격리 확인 |
| **5** | **입력·표현 분리** — `PlayerInputRouter` + `PlayerInteractor` + `IInteractable`, `OnGUI` 9곳 → uGUI, `.inputactions` 실사용 | `BB.Game`에 `Keyboard`·`OnGUI`·`Renderer` 참조 0건 |
| **6** | **`BB.Client` 분리 + NGO Host 세션 수명** + 이동 서버 권위 | Host 1대와 Client 2대가 직접 연결로 1판을 끝내고 Host 종료 시 안전하게 연결 화면으로 복귀한다 |
| **7** | **`BalanceSet` 테이블 9종 + 해시 게이트** | 코드 내 밸런스 자리표 0. 에셋만 바꿔 튜닝 |
| **8** | **Result + Steam Lobby/P2P·SDR 통합** | Steam 초대로 참가하고 2인 1팀을 짜서 Host 판을 시작·종료한 뒤 같은 Lobby로 돌아간다 |
| **9** | **텔레메트리 + 복제 범위 차단(`NetworkShow/Hide`)** | 판 1건 JSON. 남의 카페 상태가 클라 메모리에 없다 |

1·2단계는 구조 작업이 아니라 **지금 있는 게임을 검증 가능하게 만드는 일**이다. 3단계 이후를 먼저 하면 검증되지 않은 것을 리팩터링하게 된다.

## 6. 지금 하지 않는 것

| 안 하는 것 | 승격 조건 |
|---|---|
| 클라이언트 이동 예측 / 롤백 | 실측 RTT에서 조작감이 무너질 때. 2~8인 파밍·카페에 선제 도입하지 않는다 |
| Steam SDK · Steam Lobby · Steam 전송 패키지 | 직접 연결 Host/Client로 코어 루프와 한 판 수명이 검증된 뒤. 현재 프로토타입에서는 보류 |
| Host migration | Host 이탈률이 실제 운영에서 높고, 중도 종료가 제품 지표를 해칠 때 |
| 데디케이티드 서버 | Host 치트·연결 품질·경쟁 공정성이 실제 서비스 문제로 측정될 때 |
| DI 컨테이너 · 이벤트 버스 · ScriptableObject 이벤트 채널 | 도입하지 않는다. 직렬화 참조 + 인스턴스 이벤트로 충분하다 |
| 오브젝트 풀 (손님·박스) | Profiler에서 스폰 비용이 실제로 잡힐 때 |
| 어셈블리 4분할 | `BB.Client` 분리는 6단계, `BB.Data` 분리는 7단계. 그전에 쪼개지 않는다 |
| 계정 서버 · 전적 DB · 별도 매치메이킹 | Steam Lobby와 로컬 결과로 운영을 시작하고, 신뢰 가능한 영구 전적·자동 매칭이 필요할 때 |
| 리플레이 · 관전 | 서버 권위가 완성된 뒤에만 가능하다. 6단계 이후 검토 |
| ECS / Jobs / Burst 전환 | Profiler 근거가 나올 때. 8인 규모에서 나올 이유가 없다 |
| 프로세스당 다중 매치 호스팅 | 리슨 서버 구조에서는 만들지 않는다. 전용 서버로 승격할 때 다시 설계한다 |
